## 1. 建议与研究问题

推荐路线：先解决程序操作正确性与观测缺口，再改善进化调度，最后验证更大的部署邻域。保留 LLM 生成完整 `solve` 算法，以及冻结 Stage2 单次贪心评价。不把项目直接改造成只由 LLM 调参的固定 ALNS，也不立即增加到 40 轮。

待检验问题：在相同正式网络、环境、实例与计算预算下，结构正确的部署操作、基于执行证据的反馈及精英进化调度，能否提高有效候选比例，并产生优于可行父代的部署算法？

论文提供设计依据；下面的具体接口、配额、门槛是本项目的工程建议，尚无实验保证。

## 5. 分阶段实施任务

### P0-1：冻结基线与数据来源

涉及：`baselines/joint-v5/`（新增）、`tests/fixtures/`、README 第 10 节。

- 原始 C0003、C0004、关键失败源码复制归档并记录 SHA256；逐轮结果保留原产地和 run ID。
- 服务器修改实现前先用原实现导出 C0003，并保留完整 search_state、配置、模型哈希和原提交信息。当前导出会校验实现哈希；只备份源码不等于备份可复现实验。
- 为“原始 LLM”“人工修正版”“模拟候选”“新 LLM 生成”“原始 LLM 种子再进化”分别记录 origin/lineage。
- 不把原始 C0003 的旧分数直接搬成新工具环境下的成绩。

验收：任意结果可追到源码、工具、模型、数据、环境及预算；原始文件不被覆盖。

### P0-2：完整覆盖不变量与结构操作原语

涉及：新增 `joint_moves.py`，修改 `joint_tools.py`、`sandbox.py` 工具门面、`joint_artifacts.py` 导出快照；避免改动旧工具行为。

先提供纯结构操作，函数名在实现时最终确定：

- 显式重分配：输入完整映射及候选指定的 `task→target_nest` 更新；返回新映射和差分，原对象不修改。
- 显式迁巢：候选指定 old/new，原巢对应的风机继续作为任务归属新巢；new 必须是输入风机，明确它从哪个旧区域移出。
- 显式撤巢：候选提供该区域所有成员（包含旧巢自身）的新归属，不能自动选目标。
- 显式合并：候选指定源巢和目标巢，连同源巢风机一起迁移。

这些原语仅保证数据结构、完整覆盖、合法 ID 和自归属关系。不得自动选巢、重插、修复、评价、remember 或调用网络。物理不可行仍由可信评价器判断；不把原语包装成隐藏优化器。若修改了新巢所在区域，也必须在差分中列为受影响区域。

先使用少量正反例测试：撤巢后键集合完全不变；迁巢后旧巢仍有归属；合并后源巢仍存在于任务键；交换不丢任务；输入不被修改；不存在目标、缺少更新或残余自归属冲突明确失败。增加随机 ID、乱序、单点巢以及迁巢目标原属于第三个区域的案例。

验收：C0002/C0005 真实失败作为只读回归可稳定复现；新结构原语在上述场景不丢任务。不能因为出现 `del` 就静态拒绝整段程序，局部临时容器可以合法删除。

### P0-3：错误诊断和执行证据

涉及：`candidate.py`、`joint_tools.py`、必要的工具门面、`joint_search.py`、新 `joint_diagnostics.py`。

- 未定义变量增加函数名、候选行号、短源码上下文；保持当前拒绝未定义全局的行为。
- 归属错误给 `missing_ids`、`extra_ids`、非法目标、无效自身归属及总数，只展示少量示例；由真实输入集合计算，不猜测错误风机。
- 完整性失败可继续保留当前返回不可行/抛契约错误的既有区分，不为提高计数把普通不可行随意升级为接口错误。
- 添加生命周期累计计数：结构合法部署请求、不同归属部署、网络可行部署、结构无效请求、重复请求、累计可行保存、严格目标改善次数。
- 保存 first_feasible、best_observed、last_remembered、returned 四套目标及对应哈希。observed 只描述被实际独立检查的方案；返回仍按候选显式记忆契约。
- 将当前“最后一次修复之后”的窗口计数与累计计数分开，分别命名；为每次修复记录 before/after、耗时和修复结果，避免重置后误读。
- `best_observed` 与 `returned` 不同应报告，但不能偷偷改变返回解。
- 提供一个简洁的只读 analyze-run 命令，输出轮次、覆盖范围、错误、种子来源、父代比较和质量摘要。

验收：不完整部署循环不会产生有效邻域计数；只改 phase、重复部署或重复 remember 不会被报告为改善；有真实改善的模拟案例能被识别。日志截断不影响完整 JSON。

### P0-4：预算计数与缓存公平性

涉及：`joint_tools.py`、`sandbox.py`、`joint_planner.py`、`joint_benchmark.py`、身份快照。

- 审计动作预算：结构原语调用/显式邻域尝试至少计一次，避免当前只在 improve 开始 tick 一次。自编 Python 邻域仍受外部超时，不能声称已统计全部操作。
- 新增可配置外部评价请求上限，覆盖未触发网络的无效/重复调用；上限独立于未缓存网络评价预算。暂不拍定数值，先用原始 C0003 和失败案例测量正常请求分布，再冻结参数并回归。
- 统计本地工具缓存、网络服务缓存、真实推理及等待时间，区分冷/热缓存。
- 服务端新增只清缓存和计数、保留已加载模型的可信请求；不要重新训练或更改解码。
- 公平基准默认每个候选/实例采用一致冷缓存起点；真实搜索可保留加速模式，但必须记录缓存策略，不把热缓存结果当成等预算独立比较。
- 时间预算与推理次数预算分别报告。确定 greedy 不等于墙钟预算下返回方案必然确定。

验收：C0006 式重复结构无效调用可在明确请求预算内退出；预算耗尽只返回候选先前显式保存的可行解；服务缓存重置不改变单区域路线与时间，原模型不重新加载；不同基准执行顺序不再靠前序缓存系统性占优。

- 先做便宜的半径几何筛查，再调用网络；距离只排候选顺序，不替代有向网络续航审核。
- 只重新请求受影响区域；最后仍由完整部署独立验算。所有尝试受同样动作、请求、时间和推理预算。
- 首版使用保持可行并严格改进的接受规则。禁忌、模拟退火、允许暂时变差等作为后续单独开关；接受规则不得把巢数与秒混成隐式加权总分。
- 测试网络贪心的前缀可行性假设；某成员集合的网络路线不可行，不证明任何超集或该区域所有路线都不可行。

验收：至少在已知可改善的小实例上观察到结构合法的减巢/迁巢/交换；大实例效果以同预算基准为准，不要求先验必胜 C0003，也不凭玩具例声称研究优势。

## 6. 实验与验收顺序

1. 离线针对性测试：结构不变量、真实失败回归、诊断累计计数、模拟改善、父代调度、去重和恢复。无收费 API。
2. 稳定后统一跑全量回归一次；新增或失败修复后再针对性重跑，不在每次小改动后重复全量。
3. 服务器 check-model：确认原权重哈希、CUDA、环境、直接/桥接路线一致；不能用模拟权重代替。
4. 服务器无 LLM 基准：原始 C0003、人工纠错 C0003、一个清楚标记的传统部署搜索基线。固定 17 实例、同预算、同缓存策略。原始 C0004 只用于退化诊断，不能作为唯一对照。
5. 条件通过后，由用户确认新六轮收费试跑；可选择 seed C0003 的定向改进模式，以验证可行父代优化，不与从零发现混为同一实验。
6. 六轮验收：正常结束；不再持续出现缺任务/未定义变量；有实际结构合法的多种部署；完整评估候选与父代可比较；如未观察到严格改善，明确报告，不自动扩大预算。
7. 用户确认后才安排正式预算和重复实验。建议先以 3 个独立搜索种子做探索性重复，费用不足时报告单次结果，不声称统计稳定。正式重复次数按成本及先导波动另定。
8. 所有策略、预算、种子和数据划分冻结后，再选择算法并评价 87。如增加独立生成留出集，应预先冻结且不进入任何提示词或调参；不能覆盖当前 16 KDE。87 只是一个案例，不能单独支撑广泛泛化结论。

质量比较：完整可行率优先；全部实例可行的算法比较既定三目标。报告真实 102 与 KDE 分组结果、单点区域比例、最小余量、初解到最终解轨迹及总耗时。运行时间、单点巢比例与余量属于诊断，不偷偷加入主要排序。

成本比较：逻辑生成轮数、真实 API 请求数、输入/输出 token、失败请求和可取得的账单；无可靠账单时不估算成精确金额。另报 Stage2 推理次数、请求/缓存命中、CPU/GPU环境和墙钟时间。

建议分层消融，不做昂贵的全排列：A 原 v5；B 加结构原语/正确性；C 加反馈与执行观测；D 加精英调度；E 可选更大邻域。比较 LLM 的贡献时，再加相同工具与预算下的手工搜索，以及无进化的独立生成对照。必须披露各组的工具、种子和总计算成本；不能将 17 个相近 KDE 实例当作 17 次独立 LLM 搜索。

## 8. 完成标准与暂缓项

工程完成标准：结构原语正确；失败可复现且可解释；实际改善能被观测；预算与缓存口径清楚；父代调度满足显式策略；原始结果和私密配置保留；离线和服务器验收通过。

研究完成标准另算：新 LLM 子代在相同条件下完整评估，表现优于可行父代/基线，且在预先冻结的留出集上有可报告结果。软件测试通过不能代替这一标准。

暂缓：40 轮自动扩容、独立反思 LLM、复杂多岛种群、直接更换模型、Stage2 重训练、随机风况鲁棒优化、强制均衡任务、修改物理模型或用 87 调参。固定区域的精确路径参考可以后续计算，但其 gap 只描述相同分区下的路由质量，不证明机巢部署全局最优。

推荐首个可交付批次：P0-1～P0-4，然后 P1-1/P1-2；先把程序错误与搜索无效分开，再决定是否启用 P2。
